# 17 · 决定自研：从 Hermes 翻车到三框架融合（导读）★

> 来源：团长经历·自述 ｜ 团长亲口讲述

## 导读

团长换遍了框架——OpenClaw、CodeWhale、Codex、Claude Code、Hermes、CrewAI——**始终没找到能真正满足他"编排需求"的框架**。

他最早以为"我已经能确定性控制 Agent 了"，过了很久才发现：**"我根本没有控制他们。我的确是在控制，但是没有完美控制。"**

于是他想在 Hermes 上实现"硬编排"（影响模型如何思考），试了很多方法，全部翻车。泄气了一段时间后，他做了决定：

> "开发。成不成，干了才知道。"

但真要做时又发现：**从 0 开发耗不起，几年时间根本没法实现。** 所以选择了另一条路——**选 3 个成熟的智能体框架，融合成一个稳定的基座**（这就是 SynAxis 的诞生：LangGraph 编排 + DSPy 质量层 + OpenHands 执行层）。

## 认知跃迁点

1. **"我以为控制了，其实没控制"**——从"确定性控制的错觉"到认清黑盒不可完全控制的现实。
2. **别被"做不了"吓住**——AI 一直说"难度太高做不了"，但最后还是"成不成，干了才知道"。
3. **自研 ≠ 从零造**——从 0 开发耗不起，就选成熟框架融合，这是最聪明的"造"。

## 能教给学生什么

1. **换框架不是目的，满足"编排需求"才是**——市场上找不到，就自己造，这是从"使用者"到"构建者"的分水岭。
2. **"融合成熟框架"比"从零造"务实**——不重复造轮子，把最好的三个拼成自己的底座。
3. **"成不成，干了才知道"**——技术难度从来不是真正的墙，被"做不了"吓住才是。

## SynAxis 版本演进（自研之后怎么走的）

SynAxis（原名 SynBase / Substrate）从决定自研起，快速迭代出一条版本线：

| 版本 | 日期 | 里程碑 |
|---|---|---|
| v0.8.x | 07-27~30 | MVP 基线：6 节点 pipeline + router + 闭环 |
| v0.900 | 07-31 | 测试阶段入口 |
| v0.910 | 08-01 | 三阶段生命周期（需求引导→流程设计→触发迭代→归档） |
| v0.920 | 08-03 | 自主进化双循环 |
| v0.930 | 08-05 | **通用框架止损** → 重定为"非标 SOP 执行底座" |
| v0.940 | 08-08 | 跑通 DeepSeek v4 + 确立 SOP 递增纪律 |
| v0.941 | 当前 | 非标 SOP 执行底座（实验期，1.0 = 生产就绪） |

三个关键认知：

1. **三框架的具象化**：LangGraph 管编排（7 节点：router/parser/planner/verifier/executor/admin/assess）、DSPy 管 LLM 质量、sandbox 管执行——正是"编排层 + 质量层 + 执行层"的融合。
2. **v0.930 止损**：从"通用基础设施级编排智能体"重定为"非标 SOP 执行底座"——这呼应了"通用路线必死"的判断，也是一次战略收窄。
3. **版本递增纪律**：每成功跑通 1 个 SOP 复杂流程，minor 号 +1（0.941→0.942→…），约 70 次达 1.0.0。版本号 = SOP 真实跑通进度的代理计数，不是拍脑袋。
